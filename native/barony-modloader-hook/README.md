# BaronyModLoader native hook runtime

This directory is the v1 runtime authority for the installed-executable path.

BML v1 targets the installed PC game executable instead of building or patching an open-source Barony fork. The app launches the stock executable and injects a platform-specific BML hook library. On Linux the verified local implementation path is `LD_PRELOAD`; macOS and Windows still need platform-specific launch adapters before they can be claimed as verified.

Current state:

- `src/bml_hook.c` builds a Linux ELF shared object with a constructor and exported `bml_hook_init` symbol.
- `build/libbarony_bml.so` is produced by the local `Makefile`.
- `manifests/steam-371970-22630456-linux.json` mirrors the local verified Steam/Linux Barony executable identity, required symbol probe targets, and fail-closed Stash hook targets passed as `BML_HOOK_MANIFEST`; the current native hook validates the path is readable and uses compiled-in tables for probing/analysis.
- The hook validates launch inputs and writes `BaronyModLoader/reports/runtime-load-report.json` under `BML_PROFILE_DIR`; executable provenance is still enforced by the app/runtime registry before launch.
- The hook resolves required installed-binary symbols with `dlsym(RTLD_DEFAULT, mangledSymbol)` and writes `BaronyModLoader/reports/symbol-probe-report.json`.
- Stash gameplay hooks are grouped behind the abstract `linux-x86_64-direct-stash-detour` backend. When the runtime manifest contains the validated `jml.stash` package, the hook now installs the production Stash bundle by default; no `BML_STASH_ENABLE_EXPERIMENTAL_PLAYABLE` gate is required. The production bundle installs the core inventory lifecycle replacements plus access/placement replacements, binds permanent and spell-created Void Chest state to the profile-scoped inventory file, places a permanent lobby access point during eligible `assignActions`, samples `shoparea` for generated-shop placement during generated-map `assignActions`/`generateDungeon`, appends placement/load/save diagnostics to `BaronyModLoader/state/stash-diagnostics.jsonl`, records runtime multiplayer metadata with a client-side mutation guard, writes `BaronyModLoader/reports/stash-playable-install-report.json`, and only forces placement during the explicit fake-provider install self-test (`BML_STASH_PLAYABLE_INSTALL_SELF_TEST=1`). `BML_STASH_DISABLE_PLAYABLE=1` is reserved for development probes that intentionally exercise one detour mode at a time. Opt-in diagnostic modes still cover the generic detour self-test, the single `Entity::addItemToVoidChestServer` bridge, the seven-target core inventory lifecycle pass-through bridge, the seven-target access/placement/prompt pass-through bridge, optional fake-provider access/placement call-through self-test, and fake-provider state-backed core behavior self-test. A process guard skips inherited `LD_PRELOAD` in non-Barony helper processes unless `BML_HOOK_ALLOW_NON_BARONY=1` is set, so launch wrappers do not overwrite Barony reports.

Build and test:

```sh
make -C native/barony-modloader-hook clean all
make -C native/barony-modloader-hook test
make -C native/barony-modloader-hook static-readiness
```

The test target builds `build/libbarony_bml.so` plus a fake Barony symbol provider, creates temporary profile/runtime manifests, preloads both libraries into `/usr/bin/true`, and validates the JSON runtime load, symbol probe, Stash hook, generic detour self-test, opt-in Stash target detour self-test, opt-in Stash add-item pass-through install, opt-in Stash core pass-through install, opt-in Stash access/placement pass-through install plus fake-provider call-through self-test, fake-provider state-backed core behavior, and production Stash install reports with Python. The production fake-provider path uses the normal Stash runtime manifest plus `BML_STASH_PLAYABLE_INSTALL_SELF_TEST=1` to prove the bundle installs without an experimental enable flag, binds the shared Void Chest inventory used by permanent and spell-created Void Chests, creates permanent Stash chest/lid pairs on a fake Start Map and a fake generated-shop map, records the multiplayer metadata/client guard, and appends matching placement/load diagnostics without enabling those forced placements by default. The fake provider includes a backward relative branch fixture matching the installed `Entity::addItemToChest` thunk shape plus access/placement fixtures with safe patch windows. It does not prove player-facing in-game Stash behavior.

Manual smoke shape:

```sh
BML_PROFILE_DIR=/path/to/profile \
BML_RUNTIME_MANIFEST=/path/to/profile/BaronyModLoader/runtime-manifest.json \
BML_HOOK_MANIFEST=/path/to/native/barony-modloader-hook/manifests/steam-371970-22630456-linux.json \
BML_HOOK_LIBRARY=/path/to/native/barony-modloader-hook/build/libbarony_bml.so \
BML_HOOK_ALLOW_NON_BARONY=1 \
LD_PRELOAD=/path/to/native/barony-modloader-hook/build/libbarony_bml.so \
/usr/bin/true
```

Set `BML_DETOUR_SELF_TEST=1` with the fake symbol provider preloaded to write `BaronyModLoader/reports/detour-self-test-report.json`. Set `BML_STASH_DETOUR_SELF_TEST=1` to verify the exact `Entity::addItemToVoidChestServer` fake-symbol detour and trampoline call-through. Set `BML_STASH_INSTALL_ADD_ITEM_PASSTHROUGH=1` to install the process-lifetime add-item pass-through report. Set `BML_STASH_INSTALL_CORE_PASSTHROUGH=1` to install and report the seven-target core inventory lifecycle pass-through set. Set `BML_STASH_INSTALL_ACCESS_PLACEMENT_PASSTHROUGH=1` to install and report the seven-target access/placement/prompt pass-through set for `actChest`, `actChestLid`, `generateDungeon`, `assignActions`, `newEntity`, `setSpriteAttributes`, and `Language::get`; add `BML_STASH_ACCESS_PLACEMENT_SELF_TEST=1` under the fake provider to write `BaronyModLoader/reports/stash-access-placement-self-test-report.json` and prove call-through for all seven replacements, including the scoped `Open stash` prompt replacement. Set `BML_STASH_DISABLE_PLAYABLE=1` when running those one-off diagnostic modes against a Stash manifest so the production bundle does not install at the same time. Set `BML_STASH_ENABLE_EXPERIMENTAL_CORE_BEHAVIOR=1` with `BML_STASH_CORE_BEHAVIOR_SELF_TEST=1` under the fake provider to validate state-backed load/add/remove/save over `stats[0]->void_chest_inventory`, including generic `addItemToChest` and `getItemFromChest` mutations. In normal launches, enabling `jml.stash` in the runtime manifest installs the production playable bundle automatically. Add `BML_STASH_PLAYABLE_INSTALL_SELF_TEST=1` only under the fake provider to force fake Start Map and fake generated-shop `assignActions` placement during install, assert both permanent Stash chest/lid pairs were created, assert the shared inventory binding used by spell-created Void Chests is present, assert multiplayer metadata/client-guard reporting, and assert `BaronyModLoader/state/stash-diagnostics.jsonl` contains the expected placement/load events. A timed installed Steam/Linux startup probe verifies the behavior-changing detours install in the real executable and runtime-load-report can load Stash; a timed Steam/Linux quickstart probe can additionally verify a real Start Map lobby placement diagnostic, but these probes do not by themselves prove item persistence, real generated-shop placement, player-cast spell interaction, save/resume behavior, or multiplayer compatibility.

Current non-goals:

- Do not claim fully verified player-facing Stash behavior yet: verified native coverage now includes fake-symbol self-tests, analyze-only target readiness reporting, opt-in add-item/core/access-placement pass-through install reports, a fake-provider access/placement call-through self-test, a non-Barony process guard for inherited `LD_PRELOAD`, a fake-provider state-backed core behavior self-test, a non-mutating scoped placement sampler, a production Stash bundle that installs by default for enabled `jml.stash` runtime manifests in the real Steam/Linux executable and can place permanent chest/lid pairs in the fake-provider Start Map and fake generated-shop map, bind the shared inventory path used by spell-created Void Chests, report multiplayer metadata/client guard state, and a real Steam/Linux quickstart diagnostic for Start Map lobby placement. The installed Steam game still needs focused in-game verification for real generated-shop access, item persistence across death/new-run/relaunch, player-cast spell-created Void Chest binding, save/resume no-fork behavior, disabled behavior, and multiplayer metadata rejection before Stash can be called fully player-verified.
- Do not treat `native/barony-modloader-runtime/patches/` as the runtime path. Those source-fork patches are semantic reference only.
- Do not claim Windows or macOS native injection support yet.
